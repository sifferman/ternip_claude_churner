# vivado-utilization

Parse a Vitis build's `kernel_util_routed.rpt` (auto-generated by
`report_accelerator_utilization` at the end of `impl_1`) and present a clean
three-way split of every primitive type:

- **Platform (XRT)** — what the Alveo shell uses (PCIe, DDR controllers,
  HBI, AXI interconnect, reset distribution, debug bridge, …). Fixed by
  the platform; the user can't shrink this.
- **Kernel (ternip_ip)** — what the user's RTL uses.
- **Free (Unused)** — what's still available inside the User Budget. This
  is what you can grow into when scaling (more cores, larger BatchSize,
  etc.).

The skill also prints **scaling headroom multipliers**: e.g. "DSP: kernel
uses 120, 12,155 free (101× more would fit)" — directly answering "how
many more cores would fit by DSP?" or "is LUT the binding constraint?"

## When to use

Trigger when the user asks any of:

- "how much area / utilization / resources does ternip use"
- "how much is XRT / the platform / the shell taking"
- "how many cells / LUTs / FFs / DSPs / BRAMs are left"
- "how many more cores would fit"
- "what's the headroom for BatchSize=N"
- "is the design DSP-bound / LUT-bound / BRAM-bound"
- "show me the utilization report"

Or whenever the conversation drifts toward "would N cores fit on this
FPGA" — the scaling-multiplier output answers that directly.

## Inputs

One argument: a path. The skill accepts either of:

1. **A `kernel_util_*.rpt` directly** — e.g.
   `…/impl_1/kernel_util_routed.rpt`.
2. **A build directory** — e.g. `synth/pynqvivado_au250/build/xcu250_D=1024_MaxCores`.
   The skill walks that subtree and picks the most recent
   `kernel_util_routed.rpt` (falls back to `kernel_util_placed.rpt` if
   the build hasn't routed yet).

If the user gives no path, default to
`synth/pynqvivado_au250/build/<CONFIG>/hw/_x/link/vivado/vpl/prj/prj.runs/impl_1/kernel_util_routed.rpt`
under the current project; if multiple configs exist, prefer the
most-recently-modified one.

## How it works

A single Python script at `scripts/parse_kernel_util.py` does
everything — no Vivado invocation needed because Vitis already generates
the report at the end of `impl_1`.

The script:

1. Resolves the input path to a concrete `kernel_util_*.rpt`.
2. Parses the fixed-width table under `1. System Utilization`. Each cell
   value has the form `NNNNN [ NN.NN%]`; the script extracts both the
   raw count and the percentage.
3. Pulls out the rows `Platform`, `User Budget`, `Used Resources`,
   `Unused Resources` (sometimes `ternip_ip` / `ternip_ip_1` appear too;
   `Used Resources` is the authoritative kernel total).
4. Prints a three-way breakdown per resource type (LUT, LUTAsMem, REG,
   BRAM, URAM, DSP) with both raw counts and chip-total percentages.
5. Prints scaling-headroom multipliers (`unused / used`) so the user
   knows the binding constraint for growth.

## Invocation

```bash
python3 SKILL_DIR/scripts/parse_kernel_util.py <path-to-rpt-or-build-dir>
```

The script prints a human-readable report to stdout. Just relay it (or
the relevant subset) to the user. No marker-line grep needed; the
output is the deliverable.

## Reading the output

Two views are printed.

**Chip view (three-way per-resource breakdown):**

```
Resource         Platform (XRT)     Kernel (ternip_ip)        Free (Unused)     Total Chip
-----------------------------------------------------------------------------------------------
LUT          184,531  10.69%     96,775   5.61%   1,444,902  83.70%   1,726,208
LUTAsMem      25,910   3.28%     16,449   2.08%     747,833  94.64%     790,192
REG          289,740   8.38%    148,813   4.31%   3,017,447  87.31%   3,456,000
BRAM             342  12.72%         12   0.45%       2,334  86.83%       2,688
URAM               0   0.00%          0   0.00%       1,280 100.00%       1,280
DSP               13   0.11%        120   0.98%      12,155  98.92%      12,288
```

Each percentage is **of the chip's total** (Platform + User Budget), so
they add to ~100% per row.

**Scaling multipliers:**

```
LUT: kernel uses 96,775, 1,444,902 free (14.93x more would fit)
REG: kernel uses 148,813, 3,017,447 free (20.28x more would fit)
DSP: kernel uses 120, 12,155 free (101.29x more would fit)
BRAM: kernel uses 12, 2,334 free (194.50x more would fit)
```

If the user is asking about scaling to N cores, the *minimum* of these
multipliers is the rough upper bound (assuming linear per-core scaling,
which is approximately true for most ternip_ip resources but not for
shared infrastructure).

## Edge cases

- **Build never reached impl_1** — `report_accelerator_utilization`
  isn't generated. Tell the user the build needs to at least complete
  placement; falling back to `kernel_util_placed.rpt` lets us answer at
  the post-place stage (within ~5% of post-route).
- **Kernel name isn't `ternip_ip`** — the rpt's "Used Resources" row is
  the kernel total regardless of name; parser does not hardcode
  `ternip_ip`. The header SKILL.md doc mentions `ternip_ip` because
  that's this project's kernel.
- **Multiple impl runs in one project** — auto-find picks the most
  recently modified `kernel_util_routed.rpt`. If that's wrong, pass the
  exact rpt path.
